# AI Agent Badcase 记录

> 目的：记录实验室管理 AI 助手在开发、联调和上线前验证中发现的问题，明确根因、处理方式和回归要求。新增问题必须补充到本文档，不以临时口头说明代替。

## 使用规则

- 每个 badcase 必须包含：用户输入、错误表现、根因、修复策略、验证方式和当前状态。
- 涉及权限、预约写入、取消预约、确认 token 的问题，必须增加服务端测试，不能只验证模型回复。
- 涉及 LangGraph checkpoint 的问题，必须区分“模型上下文”和“本轮响应输出”。
- 任何历史工具结果都不能因为 checkpoint 恢复而再次渲染到当前回复。

## BC-001 设备接口 500

**用户表现**：`POST /api/equipment` 返回 500，ASGI 日志出现数据库异常。

**根因**：数据库查询或事务异常后没有统一回滚，异常继续向 FastAPI 冒泡；错误信息也没有形成稳定的业务错误响应。

**处理策略**：

- AI Tool 数据库异常统一执行 `rollback()`。
- API 层统一异常处理，返回可识别的错误码和用户提示。
- 结构化记录请求路径、用户、异常类型和 trace 信息，不记录密码、token 等敏感数据。

**验证**：接口异常、数据库连接中断、工具失败后下一次请求仍可正常执行。

**状态**：已处理，仍需持续观察生产日志。

## BC-002 预约信息分多轮发送后重复询问

**用户输入**：

```text
我要预约
广州化学实验室
明天下午4点到6点
```

**错误表现**：每一轮都重复询问实验室或日期时间，无法进入预约确认。

**根因**：预约流程只解析当前消息，没有将多轮字段合并到结构化状态；早期版本还把空草稿误判成没有活动流程。

**处理策略**：

- 使用 LangGraph booking 子图。
- 使用 Redis Stack Checkpointer 保存预约草稿。
- 草稿绑定 `user_id + conversation_id + workflow`。
- 增加 `workflow_active`，空草稿也能保持预约流程活动状态。
- 当前消息只覆盖当前字段，未提供的字段从 checkpoint 恢复。

**验证**：内存 checkpoint 和 Redis Stack 均验证三轮预约续接。

**状态**：已处理。

## BC-003 “继续前面的预约”落到普通聊天

**用户输入**：`继续前面的预约`。

**错误表现**：AI 返回与预约无关的普通回答。

**根因**：恢复指令不包含实验室、日期或时间字段，没有命中预约字段解析器，随后被普通聊天图接管。

**处理策略**：

- 增加预约恢复意图识别：`继续预约`、`接着预约`、`恢复预约` 等。
- 有活动 booking checkpoint 时强制进入预约子图。
- 无活动预约流程时明确提示重新开始，不交给普通模型自由发挥。

**验证**：已有 checkpoint 时恢复缺失字段或重新展示确认；无 checkpoint 时返回明确提示。

**状态**：已处理。

## BC-004 取消预约无法通过 AI 执行

**用户输入**：`帮我取消我的预约`。

**错误表现**：AI 只能查询预约，不能完成取消。

**根因**：后端普通预约页面已有取消接口，但 AI Tool 层没有取消准备工具、确认 token 和取消工作流。

**处理策略**：

- 增加 `prepare_cancel_booking`。
- 取消必须先展示确认信息，再由服务端执行写入。
- token 绑定用户、会话、预约和过期时间，并保存 hash。
- 服务端再次校验预约归属、状态和权限。
- 使用 Redis 幂等锁和数据库行锁，避免重复取消。

**验证**：本人取消、跨用户取消、重复确认、过期 token、已取消预约。

**状态**：已处理。

## BC-005 实验室简称无法识别

**用户输入**：`我要预约广州实验室，明天下午4点到6点`。

**错误表现**：数据库存在“广州化学实验室”，但 AI 提示无法识别实验室。

**根因**：早期只支持完整名称包含匹配，不支持位置、简称和候选评分。

**处理策略**：

- 完整名称优先。
- 实验室名称去除通用后缀后匹配。
- 支持位置匹配和轻度模糊匹配。
- 唯一候选自动选择，多候选必须让用户选择，禁止猜测。

**验证**：唯一简称、多候选同地点、停用实验室和无匹配结果。

**状态**：已处理。

## BC-006 结构化卡片重复或正文过长

**用户表现**：卡片已经展示详情，正文又重复表格或出现“详情已按卡片展示”等内部说明。

**根因**：工具结果和模型正文同时承担展示职责，摘要函数没有严格限制输出内容。

**处理策略**：

- 卡片负责详细数据展示。
- 正文只保留一句事实摘要。
- 不向用户暴露“生成卡片”“工作流”等内部实现术语。

**状态**：已处理，需继续做前端视觉回归。

## BC-007 checkpoint 历史工具结果污染当前回复

**用户输入**：`帮我看下有哪些实验室开放`。

**错误表现**：

```text
当前有 2 间开放实验室。
已查询到 5 个用户。
当前有 4 间开放实验室。
```

**根因**：LangGraph checkpoint 保留完整历史是正确的，但响应渲染遍历了整个 checkpoint 的 `ToolMessage`，没有只读取本轮新产生的工具结果。

**处理策略**：

- 调用图前读取 checkpoint 中已有消息数量。
- 调用图后只处理本轮新增消息范围。
- 卡片聚合和正文摘要只基于本轮工具结果。
- 历史结果只用于模型理解，禁止再次渲染。

**验证**：先查询用户，再查询实验室；当前实验室查询不能出现用户卡片或旧实验室数量。

**状态**：已修复，待真实页面回归。

## BC-008 上下文与业务权限混淆

**错误表现**：用户消息或知识库文本试图声明管理员权限、修改规则或调用内部工具。

**根因**：把自然语言上下文当成可信权限来源。

**处理策略**：

- 用户身份、角色和资源归属只由服务端提供。
- Tool 层做最终权限校验。
- 知识库和工具返回值视为不可信数据。
- 写操作必须经过显式确认和服务端二次校验。

**状态**：已处理，需持续扩充对抗性测试。

## BC-009 清空或新建会话后带入旧内容

**用户操作**：清空当前会话，或点击新建会话后继续提问。

**错误表现**：前端显示已清空，但后续 AI 仍然带入上一会话的聊天内容、预约草稿或工具结果。

**根因**：前端只清空了本地消息数组，后端 `conversation_id`、数据库会话、LangGraph checkpoint 和预约工作流状态仍被复用。

**处理策略**：

- 新增服务端会话 reset 接口，并校验会话属于当前用户。
- reset 时归档旧会话、将未完成工作流标记为 `reset`。
- 删除旧会话对应的 chat 和 booking checkpoint。
- 服务端生成新的 UUID 作为新会话 ID。
- 前端清除旧会话缓存、确认 token 和消息状态。
- 旧消息保留用于审计，但不再被新会话加载。

**验证**：清空后发送实验室查询、预约续接和普通问题，均不能读取上一会话内容；跨用户 conversation ID 不能访问或重置他人会话。

**状态**：已处理，待真实浏览器回归。

## BC-010 预约请求中的设备没有写入

**用户输入**：`我要预约明天下午1点到2点，化学实验室下的显微镜设备`。

**错误表现**：预约流程可以识别实验室和时间，但确认信息中的设备为空，最终预约没有关联设备。

**根因**：早期 `resolve_booking_request()` 只解析实验室、日期和时间，最终固定返回 `equipment_ids: []`，没有从当前实验室下的设备中解析名称，也没有把设备 ID 传给预约准备工具。

**处理策略**：

- 只在已确定的实验室范围内搜索可预约设备。
- 支持设备名称、设备类型、型号和“设备/仪器”简称匹配。
- 唯一匹配后将设备 ID 写入预约草稿和 `prepare_create_booking` 参数。
- 多个设备候选接近时要求用户选择，禁止猜测。
- 用户明确提到设备但没有匹配结果时，阻止预约确认并提示补充设备名称。
- 最终仍由 `BookingService._validate_resources()` 校验设备归属、启用状态和维护状态。

**验证**：化学实验室 + 显微镜设备的预约确认中必须出现设备；跨实验室设备、停用设备和多设备同名场景必须失败或要求选择。

**状态**：已处理，待真实预约确认回归。

## BC-011 预约冲突被误报为数据查询失败

**用户输入**：`帮我预约明天1点到2点的化学实验室下显微镜设备`。

**错误表现**：系统返回“数据查询暂时失败，请稍后重试”。

**根因**：实际数据库返回的是实验室时间段冲突，但 AI Tool 将所有异常统一包装成数据库查询失败，隐藏了真实业务原因。

**处理策略**：

- `BusinessExceptions` 单独归类为业务规则错误。
- 时间冲突返回明确提示，不标记为可重试的数据库故障。
- 数据库连接、SQL 和未知异常继续记录结构化日志并返回通用失败提示。
- 预约确认前仍然重新执行时间和设备冲突校验。

**验证**：已预约时段返回“实验室时间段已被占用”；数据库异常仍返回可重试错误。

**状态**：已处理。

## BC-012 查询预约被误判为创建预约

**用户输入**：

```text
先取消我的预约，取消成功后再问：现在还有哪些预约？
```

**错误表现**：取消成功后，查询预约列表时又返回：

```text
请补充预约日期与时间段，我再确认预约信息。
```

**根因**：早期 `_has_booking_intent()` 只要发现文本包含“预约”就判定为预约创建意图。查询结果虽然已经生成 `booking_list`，但后处理只把预约确认和预约提交视为有效结果，仍然追加了创建预约的补充提示。本问题不是 checkpoint 丢失，而是意图分类过宽和结果后处理缺少保护。

**处理策略**：

- 将创建预约意图与查询预约意图分开。
- `我的预约`、`预约记录`、`有哪些预约`、`查看预约` 等查询短语不再进入创建预约流程。
- 只有明确的创建预约意图才允许追加“请补充预约日期与时间段”。
- `booking_list`、取消预约卡片和预约结果均视为本轮已完成业务响应，禁止追加创建预约提示。
- 保留 checkpoint 作为上下文来源，但不让历史状态覆盖当前问题的明确查询意图。

**验证**：

- `现在还有哪些预约` 必须返回预约列表。
- `我的预约有哪些` 必须返回预约列表。
- `帮我预约化学实验室` 可以进入创建预约流程。
- `我要预约` 缺少时间时才提示补充日期和时间段。
- `取消我的预约` 继续进入取消预约流程。
- `继续前面的预约` 继续进入预约 checkpoint 恢复流程。

**状态**：已处理，已通过意图分离断言、AI 工具测试、综合功能测试和前端构建。

## BC-013 相对日期和预约时段提示不准确

**用户输入**：

```text
帮我预约医学实验室
一周后的下午1点到2点
```

**错误表现**：系统提示同时补充具体日期和时间段，并声称无法自行换算“一周后”；用户已经提供了时间范围，但未得到准确反馈。

**根因**：确定性日期解析器未覆盖“一周后/一周以后/7天后”等相对日期；日期或时间任一缺失时统一返回同一条补充提示；固定两小时预约规则也没有在预约解析层给出独立的校验结果。

**处理策略**：

- 将“一周后”“一周以后”“一星期后”“7天后”解析为当前业务时区日期加 7 天，并支持“两周后/14天后”。
- 将缺少日期、缺少时间、日期和时间都缺少拆分为不同原因和中文提示，保留已识别字段。
- 在预约解析层显式校验标准时段，当前允许 `08:00–10:00`、`10:00–12:00`、`14:00–16:00`、`16:00–18:00`、`19:00–21:00`。
- 对 `13:00–14:00` 返回具体日期、具体非法时段和可选标准时段，不交给模型猜测。

**验证方式**：标准库回归测试验证相对日期、中文上午/下午时间解析和标准时段校验；后续应补充真实数据库下的预约预览及冲突校验回归。

**状态**：已处理，已通过 `backend/test_booking_workflow.py` 3 项回归测试。

## BC-014 当前预约查询包含已取消历史记录

**用户输入**：

```text
先取消我的预约，再问：现在还有哪些预约？
```

**错误表现**：预约已经成功取消，但“现在还有哪些预约”仍返回这条已取消记录，并显示为当前预约。

**根因**：预约查询工具默认查询当前用户的全部预约记录，没有区分“当前有效预约”和“历史预约记录”。

**处理策略**：

- “现在还有哪些预约”“当前预约”“我的预约”等默认只查询 `待审核` 和 `已批准`。
- 用户明确询问“预约记录”“全部预约”或“所有预约”时才查询包含历史状态的记录。
- 查询入口由后端确定性路由控制，不交给模型自行决定过滤语义。

**验证方式**：真实浏览器中完成创建、确认、取消、再次查询全链路；取消后查询返回 0 条当前预约。新增标准库回归测试验证 active 查询排除已取消记录。

**状态**：已处理，已通过真实浏览器回归和 `backend/test_booking_query.py`。

## BC-015 预约业务入口分散导致意图互相污染

**用户表现**：同一类消息在不同路径中被重复判断，查询、资源查询和预约创建可能出现重复提示或错误进入普通模型。

**根因**：旧实现由多个 `_run_explicit_*` 函数各自调用意图判断；预约流程还额外读取 checkpoint 判断是否续接，导致同一请求存在多套判定结果。

**处理策略**：

- 由 `app/services/agent_router.py` 统一生成一次 `RouteDecision`。
- 路由决策结合当前预约 workflow 是否活跃，支持“下一轮只补时间/日期”的续接场景。
- 取消、预约查询、资源查询和预约创建入口只接受匹配的路由结果。
- 普通模型只处理未命中确定性业务路由的请求。

**验证**：增加资源查询、预约查询、预约创建、取消和 workflow 续接的路由回归测试；完整单测和前端生产构建通过。

**状态**：已处理。

## BC-016 带实验室名称的取消请求被误判为创建预约

**用户输入**：`帮我取消广州化学实验室的预约`

**错误表现**：系统要求补充预约日期和时间，进入了创建预约流程。

**根因**：旧路由只匹配连续短语“取消预约”。当实验室名称插入“取消”和“预约”之间时，取消意图没有命中，而“预约”又触发了创建预约判断。

**处理策略**：

- 取消路由支持“取消 + 任意预约对象 + 预约/预订”的组合表达。
- 取消流程支持从当前用户自己的有效预约中按实验室名称唯一匹配。
- 同一实验室存在多条预约时，只返回该实验室的选择卡片，不要求用户重新填写创建预约字段。
- 仍然必须经过取消确认 token，不能因为名称匹配直接写库。

**验证**：新增 `帮我取消广州化学实验室的预约` 路由回归测试，并通过 13 项后端单测和 AI 工具安全测试。

**状态**：已处理。

## BC-017 管理员查询其他用户待审批预约被误判为创建预约

**用户输入**：`目前其他用户有哪些需要审批的预约`

**错误表现**：系统提示补充预约日期和时间，进入创建预约流程。

**根因**：原有预约查询只覆盖“我的预约”，没有单独定义“其他用户/待审核”的管理员查询意图。

**处理策略**：

- 新增 `ADMIN_BOOKING_QUERY` 路由。
- 新增管理员专用 `list_pending_bookings` 工具。
- 工具服务端校验当前用户必须是管理员，普通用户不能查询他人预约。
- 返回待审批预约卡片，包含预约人、实验室、设备、时间和状态。
- 该路由不会进入创建预约工作流，也不会要求预约日期和时间。

**验证**：新增管理员待审批查询路由测试和普通用户工具越权测试，14 项后端单测全部通过。

**状态**：已处理。

## BC-018 管理员待审批查询缺少时间范围建模

**用户输入**：

```text
今天有需要审批的预约吗
最近一个月有需要审批的预约吗
```

**错误表现**：系统只能查询全部待审批预约，或者无法区分查询范围，容易继续退化成按关键词补丁。

**根因**：管理员待审批查询只建模了固定状态，没有把时间范围作为结构化查询过滤器。

**处理策略**：

- 保持单一 `ADMIN_BOOKING_QUERY` 意图。

## BC-019 SSE 连接存在但回复仍然整块输出

- 错误时移除未完成的临时消息，避免残留半截结果。

**验证**：增量事件单测通过，后端 16 项单测、AI 工具安全测试和前端生产构建通过。

## BC-021 多轮预约示例时间无法识别且局部槽位丢失

**用户对话**：

```text
帮我预约广州实验室
对，就这个时间
明天 14:00–16:00
14:00–16:00
```

**错误表现**：助手把短确认语当作无法识别的新意图；随后无法识别 `14:00–16:00` 中的长横线，并反复要求补充日期或时间。首轮识别到的日期/时间片段也没有可靠保存在预约草稿中，导致跨轮无法合并。

**根因**：预约状态同时存在于数据库 workflow JSON 与 LangGraph checkpoint，但有活动 checkpoint 时编排层不再注入数据库中的权威草稿；部分日期/时段只在一轮内解析，未形成可合并的结构化字段。路由上下文也未提供上一轮助手追问，模型无法可靠区分“确认示例”与“提供具体槽位”。时间解析器还未统一 Unicode 横线。

**处理策略**：

- 归一化 Unicode 横线和全角字符，兼容 `14:00–16:00` 等常见输入。
- 将日期和时段分别保存在预约草稿中，允许先日期后时段或先时段后日期合并。
- 数据库 workflow 状态作为预约草稿的唯一权威来源；每轮都显式注入 LangGraph，checkpoint 只负责流程恢复。
- 将上一轮助手追问作为结构化上下文交给意图解析器；自然语言分类负责识别续接，领域解析器只保存用户本轮明确提供的日期/时段。
- 对已完整但校验失败的草稿，只有本轮明确更新槽位后才重新调用预约准备工具，避免确认语重复触发。
- 增加 SQLite 多轮回归、路由隔离测试和 CONT-13 至 CONT-15 评测样例。

**验证**：预约解析、状态图多轮集成与路由隔离回归通过；后端全量 unittest 22 项、意图路由合同测试 21 项、Python 编译检查及 `git diff --check` 均通过。

**状态**：已处理。

## BC-022 明确的“确认预约”未通过确认契约

**用户输入**：预约信息已准备完成且带有有效 confirmation token 时，用户输入 `确认预约`。

**错误表现**：系统没有提交预约，反而进入普通意图路由并要求用户重说需求。这个说法明确但不在确认语白名单内。

**根因**：确认是一个服务端安全门禁，但原契约只匹配部分固定短语；缺少常见、意图清晰的确认表达。

**处理策略**：

- 将 `确认预约` 和 `确定预约` 增加为精确匹配的预约确认语。
- 仍强制校验有效 token、用户归属、workflow 状态及幂等锁；不将宽泛“好/可以”等表达放行为确认。
- 增加确认契约单测和实际聊天 API + Redis Stack 多轮回放。

**验证方式**：真实模型四轮补齐预约信息，确认前隔离 SQLite 中为 0 条预约；使用 `确认预约` 提交后只创建 1 条，工作流标记为已消费、Redis checkpoint 被清理；重放相同 token 不会创建第二条。

**状态**：已处理；确认白名单的单测和实际 API 回放通过。

## BC-023 重复确认被包装为成功响应

**用户操作**：预约已成功提交后，客户端因重试再次发送相同 confirmation token。

**错误表现**：数据库正确阻止重复写入，但 API 返回 HTTP 200 和 `code=200`，错误包络看起来像成功。

**根因**：业务异常处理器固定使用 HTTP 200，`BusinessExceptions` 默认业务码也为 200；前端只能从缺少聊天数据间接判断失败。

**处理策略**：

- 业务异常默认使用 HTTP 400；冲突、已消费或失效的预约确认使用 HTTP 409。
- 错误包络中的 `code` 与 HTTP 状态码保持一致，响应结构固定为 `code/message/data`。
- 参数验证日志只记录请求路径、字段位置和错误类型，不记录请求体或输入值。
- 前端通用 `request()` 已将所有非 2xx 响应转换为 `ApiError`，无需添加平行的业务判断。

**验证方式**：FastAPI 契约测试覆盖 400、403、409、422；真实模型 + Redis Stack 回放确认前预约数为 0，首次确认后为 1，重复 token 返回 409 且仍为 1；验证请求值不进入日志和错误响应。

**状态**：已处理；后端 29 项测试、前端生产构建和真实 API 重放通过。

## BC-024 业务异常状态码不准确且 AI 工作流吞掉领域错误

**用户表现**：登录凭据错误、资源不存在、预约冲突、无效输入和 AI 服务故障有时都被统一返回为 400；预约流程中的 404、409、422 还可能被 AI 编排层捕获后改写为通用错误。

**根因**：服务层没有按认证、权限、资源、冲突、输入校验和上游服务故障区分 HTTP 状态；多个 AI 工作流使用宽泛异常捕获，把已知领域异常与未知基础设施故障混为一类。确认预约失败时，幂等锁也缺少覆盖所有退出路径的释放逻辑。

**处理策略**：

- 认证失败使用 401，权限拒绝使用 403，资源不存在使用 404，状态冲突使用 409，输入校验使用 422。
- 上传大小限制和文件类型错误分别使用 413、415；模型上游空响应使用 502，模型未配置或 AI 工作流基础设施故障使用 503。
- AI 工作流先回滚并原样抛出已知业务异常；仅将未知异常记录为服务暂不可用，避免覆盖领域状态码。
- 预约确认失败时回滚数据库事务并在 `finally` 释放幂等锁；确认已成功写库后，checkpoint 清理失败只记录服务端日志，避免把已完成的预约误报为失败。
- 用 HTTP 契约测试覆盖 401、403、404、409、413、415、422、502、503，并针对认证、用户、预约及 AI 编排层增加映射回归。

**验证**：后端全量 unittest 36 项通过；实际上传 API 返回 413/415；认证、资源、预约与 AI 工作流状态映射回归通过；前端生产构建通过；`git diff --check` 通过。前端构建提示主 JS chunk 超过 500 kB，不影响本次构建结果，建议后续按路由拆分。

**状态**：已处理；契约、服务映射和上传端点回归通过。
