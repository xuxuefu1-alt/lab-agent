# 多意图计划编排

## 1. 目标

多意图请求不能被压缩成一个模糊标签，也不能直接交给通用模型自由决定执行顺序。
系统应先识别用户提出的多个业务目标，再生成可验证、可暂停、可恢复的执行计划。

典型请求：

> 帮我看下我目前有哪些预约，然后帮我取消了

生产级处理顺序：

```text
识别多意图
  -> 生成有序计划
  -> 查询本人预约
  -> 展示候选预约
  -> 等待用户选择
  -> 生成取消预览
  -> 等待用户确认
  -> 重新校验并执行取消
```

任何写操作都必须经过领域服务、权限校验、归属校验、状态校验和确认令牌校验。

## 2. 分层边界

### Router

负责自然语言理解：

- 判断单意图或多意图
- 输出 `speech_act`
- 提取用户明确提供的槽位原文
- 生成 `IntentPlan`
- 标记歧义、缺失字段和澄清问题

Router 不负责权限判断，不负责生成数据库 ID，不负责决定是否可以执行写操作。

### Plan Orchestrator

负责计划执行控制：

- 校验计划结构和步骤依赖
- 决定执行顺序
- 管理暂停点和恢复点
- 保存候选集合和当前步骤
- 解析用户对候选集合的选择
- 将写操作转交领域工作流

编排器不直接写数据库，不绕过工具网关，不使用历史文本猜测目标对象。

### Domain Workflow

负责预约查询、创建、取消和业务状态规则，包括：

- 用户归属
- 预约状态
- 实验室和设备解析
- 时间冲突
- 是否允许取消
- 领域错误和可重试错误

### Tool Gateway

负责工具调用的统一约束：

- 认证和授权
- 参数 schema 校验
- 超时、重试和熔断
- 幂等键
- 调用审计
- 脱敏日志

## 3. 计划模型

当前计划模型由 `IntentPlanStep` 和 `IntentPlan` 组成，定义在：

```text
backend/app/services/agent_router.py
```

示例：

```json
{
  "mode": "sequential_dependent",
  "steps": [
    {
      "step_id": "query_bookings",
      "intent": "booking_query",
      "order": 1,
      "depends_on": [],
      "purpose": "查询当前用户可处理的预约",
      "requires_selection": false,
      "requires_confirmation": false
    },
    {
      "step_id": "cancel_booking",
      "intent": "cancel_booking",
      "order": 2,
      "depends_on": ["query_bookings"],
      "purpose": "取消用户选择的预约",
      "requires_selection": true,
      "requires_confirmation": true
    }
  ]
}
```

约束：

- `step_id` 在一个计划内必须唯一。
- `order` 必须形成确定顺序。
- `depends_on` 只能引用当前计划中的步骤。
- 依赖图不能有环。
- 需要选择的步骤必须先拥有受服务端控制的候选集合。
- 需要确认的步骤不能直接执行写操作。
- 计划不能包含未注册的意图或工具。

## 4. 计划类型

### sequential_dependent

前一步的结果决定后一步的输入。

适用场景：

- 查询预约后取消其中一条
- 查询候选设备后选择设备并预约
- 查询审批记录后执行用户指定的审批动作

处理要求：前一步完成后保存结构化结果，并在依赖满足前暂停。

### sequential_independent

多个步骤互不依赖，但需要按固定顺序返回结果。

适用场景：

- 查询我的预约，再查询我的待办
- 查询实验室目录，再查询设备目录

所有步骤默认只读；如果包含写操作，应拆分为独立的确认阶段。

### parallel_independent

多个只读步骤互不依赖，可以并行执行。

适用场景：

- 同时查询实验室目录和设备目录
- 同时查询预约、通知和审批状态

并行执行必须设置独立超时、部分失败策略和结果合并规则。写操作不应直接进入并行计划。

## 5. 状态机

```text
RECEIVED
  -> PLANNED
  -> RUNNING_STEP
  -> WAITING_SELECTION
  -> RUNNING_STEP
  -> WAITING_CONFIRMATION
  -> EXECUTING_WRITE
  -> COMPLETED
```

异常状态：

```text
RUNNING_STEP -> FAILED_RETRYABLE
RUNNING_STEP -> FAILED_TERMINAL
WAITING_SELECTION -> EXPIRED
WAITING_CONFIRMATION -> EXPIRED
```

状态中至少保存：

- `plan_id`
- `plan_version`
- `plan_mode`
- `source_question`
- `current_step`
- `completed_steps`
- `candidate_ids`
- `candidate_snapshot`
- `selection_required`
- `confirmation_required`
- `created_at`
- `expires_at`
- `last_error_code`

候选快照只用于恢复用户选择，不代表最终可执行状态。真正执行取消前，必须重新查询并校验预约归属和当前状态。

## 6. 查询后取消的标准流程

### 第一步：查询

调用 `list_my_bookings`，只返回当前认证用户有权查看的预约。

查询失败时：

- 不创建取消确认令牌
- 不进入取消工具
- 返回可重试错误
- 记录失败步骤和错误码

查询为空时：

- 结束计划
- 返回没有可取消预约
- 不创建后续状态

查询有结果时：

- 保存候选 ID 和候选快照
- 将状态置为 `awaiting_selection`
- 返回选择卡片
- 等待用户指定序号、预约 ID 或候选名称

### 第二步：选择

选择解析只能命中本次查询返回的候选集合：

- `取消第 2 条`
- `取消预约 123`
- 直接输入候选 ID
- 输入候选实验室名称

无法唯一命中时必须继续澄清，不能根据历史文本或模型猜测目标。

### 第三步：确认

选中目标后调用既有取消工作流，生成取消预览和一次性确认令牌。

用户确认后，服务端必须再次执行：

- 确认令牌校验
- 用户归属校验
- 预约当前状态校验
- 幂等锁校验
- 取消写操作

用户拒绝、令牌过期或预约状态变化时，应清理对应计划状态并返回明确结果。

## 7. 失败与恢复

### 可重试失败

例如工具超时、Redis 临时不可用、下游服务暂时不可用。应保留计划上下文，但限制重试次数，并返回稳定错误码。

### 不可重试失败

例如无权限、预约不存在、预约已经取消、候选不属于本用户。应结束当前步骤，清理写操作确认状态，并要求用户重新发起明确请求。

### 状态过期

选择和确认状态必须设置过期时间。过期后：

- 不再接受旧的候选 ID
- 不再接受旧确认令牌
- 删除或标记过期状态
- 提示用户重新查询

## 8. 审计与可观测性

每个计划和步骤都应有结构化事件，至少包含：

- `trace_id`
- `conversation_id`
- `plan_id`
- `plan_mode`
- `plan_step`
- `plan_status`
- `blocked_reason`
- `selection_required`
- `confirmation_required`
- `router_version`
- `tool_name`
- `latency_ms`
- `error_code`

日志中不得写入确认令牌、密码、完整认证信息或未脱敏的敏感个人信息。

## 9. 测试门禁

生产交付前至少覆盖：

- 模型漏返回计划时的确定性补全
- 查询后取消的顺序约束
- 查询失败、查询为空、工具超时
- 候选外 ID 和模糊名称
- 用户选择后预约状态变化
- 确认、拒绝、过期、重复提交
- 多步骤部分失败
- 并行只读任务的部分成功
- 任意模型输出都不能绕过权限和确认

高风险门禁：

- 未确认时不得发生取消写入
- 候选外对象不得进入取消工作流
- 无权限用户不得通过自然语言声明提升权限
- `multi_intent` 不得降级为终止式澄清

## 10. 当前实现与后续路线

当前已落地：

- `IntentPlan` 结构化计划
- `sequential_dependent` 查询预约后取消
- 候选集合持久化
- 只从候选集合解析用户选择
- 取消工作流继续使用独立确认令牌和幂等校验
- 计划生命周期写入结构化日志、OpenTelemetry span 和 Prometheus 指标
- 支持 `sequential_independent` 与 `parallel_independent` 的只读计划执行
- 定向、质量和后端回归测试

后续按以下顺序推进：

1. 为计划状态增加过期清理、重试上限和恢复接口。
2. 将多意图回归纳入 CI 质量门禁和离线评测报告。
