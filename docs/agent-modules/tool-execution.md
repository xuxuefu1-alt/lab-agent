# 工具执行与授权边界

## 目标

让 Agent 工具成为明确、有限、可审计的业务 API。模型可以提出工具调用意图，但工具执行权、用户范围、业务校验、事务和最终结果均由服务端控制。

## 当前基础与缺口

- `backend/app/services/ai_tools.py` 已使用 Pydantic 参数模型，部分字段有范围和长度约束。
- 工具按当前登录用户构造，并对管理员专用查询做服务端角色校验。
- 预约创建/取消工具先返回待确认信息，真正写库由后端确认流程完成。
- 工具目前通常把 JSON 编码成字符串返回，失败类型不统一；通用异常被包装后难以判断可重试性。
- Agent 入口与 REST API 的授权策略不一致；实验室、设备写接口缺少管理员校验，绕开工具层即可执行管理操作。
- 需要统一超时、审计关联 ID、幂等策略和错误语义。

## 工具分层

### 只读工具

- `search_laboratories`
- `search_equipment`
- `check_availability`
- `list_my_bookings`
- `list_pending_bookings`（管理员）
- `retrieve_policy`

只读工具按用户范围过滤数据；检索用户身份和角色只能来自认证上下文，不能接收模型传入的 `user_id` 来扩大查询范围。

### 写操作工具

模型侧只暴露“准备/预览”能力：

- `prepare_create_booking`
- `prepare_cancel_booking`
- 后续确有需求时再增加 `prepare_update_booking`、`prepare_approval`。

实际写库通过专用服务端工作流完成：确认状态有效、校验确认人、重查资源和权限、检查幂等记录、执行事务、生成审计事件。通用问答图不得持有可直接写库的 Tool。

## 统一工具契约

工具输入必须严格校验：

- `extra="forbid"`，拒绝未定义字段。
- 字符串、分页、列表长度和 ID 范围设定上限。
- 时间使用明确的时区和统一格式；服务端再次校验可预约规则。
- 用户、角色、租户和操作者 ID 由依赖注入，不接受模型传值。

工具返回统一对象，不再让调用方解析 JSON 字符串：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "BOOKING_CONFLICT",
    "message": "该时段已被预约，请选择其他时段。",
    "retryable": false
  },
  "run_id": "..."
}
```

规则：

- `error.code` 使用稳定枚举；不要把 SQL、堆栈、供应商异常或密钥发给模型/用户。
- 只有可安全重试的外部依赖错误才标记 `retryable=true`。
- 数据库异常、业务冲突、无权限、输入错误必须分开处理。
- 工具输出只包含完成当前决策所需的最少个人数据。

## 授权与业务策略

- REST API 和 Agent 工具调用同一领域服务及授权策略；不能只在前端隐藏按钮。
- `student` 只能查看自己的预约；`admin` 查询其他用户数据和审批时，服务端再次校验角色及目标范围。
- 对组织/学院多租户部署时，将 `tenant_id` 放入认证上下文并在查询层统一过滤。
- 创建、修改、批准、取消前重新验证资源状态和业务约束，不信任早先预览。
- 管理员资源写操作需专门权限策略；当前 lab/equipment 写接口应先修复角色检查。

## 幂等、事务与审计

- 每个写请求拥有服务端认可的 `idempotency_key`，数据库保存执行状态和结果；重试返回原结果，不重复写入。
- Redis 锁可做并发协调，但不能替代数据库约束和事务。
- 所有锁释放放在 `finally`；数据库事务负责原子地消费确认状态并写入业务记录。
- 审计至少记录 `run_id`、操作者、action、资源 ID、策略结果、结果状态和时间；敏感正文脱敏。
- 为操作设计明确状态转移，例如 `prepared -> confirmed -> executing -> completed/failed/expired`。

## 超时与失败行为

- 给数据库、模型、向量检索和外部服务分别配置超时。
- 只对读操作和安全幂等操作进行有限次数退避重试。
- 写操作超时结果不明确时，先通过幂等记录查询结果，不能盲目重放。
- 不允许 `except Exception` 后统一返回“查询失败”而丢失业务错误类别；保留结构化内部日志但不给用户暴露内部细节。

## 验收门槛

- 匿名用户和普通用户无法调用管理员工具或写资源接口。
- 提示注入、伪造 user ID、额外字段和越界参数不能提升权限或改变资源归属。
- 同一幂等写请求并发/重试只产生一次副作用。
- 冲突、越权、无效参数、数据库故障分别返回稳定错误码。
- 预约确认前及提交时都重新校验资源和权限；失败后工作流可解释、可恢复。
