# 会话记忆与工作流状态

## 目标

让对话上下文、预约草稿、工具执行状态和审计数据有明确的事实来源、生命周期和恢复行为。记忆用于帮助理解上下文，不得替代业务数据库或授权决策。

## 当前实现

- `AiConversation`、`AiMessage` 和 `AiWorkflowState` 保存数据库中的会话、消息和预约流程状态。
- LangGraph checkpoint 保存图状态；生产模式要求 Redis Stack，开发模式允许进程内 checkpoint。
- 对话上下文使用最近消息和 conversation summary；预约状态单独存储，设计方向合理。
- summary 当前由旧 summary 与近期消息片段拼接截断，不是语义化且经过验证的状态摘要。
- 同一对话历史同时存在数据库消息和 LangGraph chat checkpoint，必须防止重复拼接、版本错位和并发顺序问题。
- 前端还将会话和确认令牌保存在浏览器本地，服务器缺少完整的会话列表/历史读取闭环。

## 事实来源划分

| 数据 | 权威来源 | 用途 |
|---|---|---|
| 用户、角色、账号状态 | 用户/认证数据库 | 每次请求权限校验 |
| 预约、设备、实验室状态 | 领域数据库 | 实时业务事实 |
| 对话原文 | `AiMessage` | 可追溯会话历史，按保留策略管理 |
| 对话摘要 | `AiConversation.summary` | 降低上下文长度；不是业务事实 |
| 预约草稿、确认相位、缺失字段 | `AiWorkflowState` | 可审计、可恢复的业务流程状态 |
| LangGraph checkpoint | Redis Stack | 图节点恢复和短期执行上下文，不作为预约事实来源 |
| 审计事件 | `AiAuditLog` 或领域审计表 | 追踪操作和合规审查 |

模型不得因为摘要写着“用户是管理员”就提升权限；每次调用都从认证上下文获取用户和角色。

## 状态模型

对话状态建议至少包括 `active`、`archived`、`deleted`；删除是产品语义，需与审计保留规则区分。

预约工作流应使用版本化 schema，例如：

```json
{
  "schema_version": 3,
  "workflow_type": "create_booking",
  "phase": "collecting_requirements",
  "status": "pending",
  "draft": {
    "laboratory_id": 12,
    "equipment_ids": [],
    "start_time": null,
    "end_time": null,
    "purpose": "实验室/设备预约",
    "student_count": 1
  },
  "missing_fields": ["date", "time"],
  "policy_version": "booking-policy-v3",
  "expires_at": "...",
  "version": 1
}
```

字段要求：

- 状态转移由服务端状态机执行，不允许模型直接修改 `phase`、`status` 或 `user_id`。
- `schema_version` 变更需提供迁移器；不能只写版本号而不转换历史状态。
- `policy_version` 记录生成草稿时适用的业务规则，提交时仍按当前规则重验。
- 每次状态更新使用乐观锁版本或行锁，避免两条并发消息覆盖彼此。

## 对话上下文构造

建议仅提供：

1. 系统指令与当前能力边界。
2. 结构化预约状态摘要（仅在相关时提供）。
3. 经标注为不可信对话数据的语义摘要和最近 N 条消息。
4. 本轮用户消息。

通过 Token 计数而不是字符数控制上下文预算；超预算时优先压缩非业务对话，不丢失尚未完成流程的关键字段。知识库文本和工具结果必须与系统指令区分，并视为不可信内容。

摘要应保留事实、来源、时间和不确定字段，例如“用户尚未确认具体设备”；不要把模型推断改写成用户已确认事实。摘要更新失败时应回退到最近消息，而不是阻断业务。

## 消息顺序与并发

- `sequence = max(sequence) + 1` 在并发请求中可能产生重复序号或乱序。
- 增加数据库唯一约束 `(conversation_id, sequence)`，并通过会话行锁、原子计数器或事务化写入分配顺序。
- 对同一会话的生成请求做并发控制；同一会话已有运行时，明确选择排队、拒绝并提示或取消旧运行。
- 所有用户和助手消息、工具调用摘要、审计记录按清晰的事务边界提交。

## Checkpoint 生命周期

- Redis checkpoint 用于快速恢复，不得替代数据库中的预约草稿与审计状态。
- `thread_id` 必须绑定用户、会话和 workflow 类型，不能由客户端任意指定。
- reset/delete 时同步清理 chat 与 booking checkpoint、数据库 workflow 状态和前端缓存。
- checkpoint 缺失或 Redis 暂时不可用时，以数据库工作流状态恢复关键业务；无法安全恢复时要求用户重新确认，不猜测状态。
- 对持久化消息、审计和 checkpoint 分别定义保留和清理策略。

## 用户数据与生命周期

- 提供服务端会话列表、历史读取、归档和删除接口，并校验会话属于当前用户。
- 明确删除、归档和合规审计保留之间的区别；UI 不能把“隐藏”描述为物理删除。
- 定义消息、摘要、工具结果、审计和确认令牌的保留期限及访问权限。
- 确认令牌只短期保存，成功、拒绝、过期或 reset 后清理。

## 实施步骤与验收

- [ ] 记录并批准数据来源划分和 schema 版本策略。
- [ ] 建立工作流状态迁移器与版本冲突保护。
- [ ] 修复消息序号并发问题，新增同会话并发处理策略。
- [ ] 实现服务端会话列表/历史读取及删除策略。
- [ ] 用 Token 预算替代单纯字符预算；明确摘要失败回退。
- [ ] 验证重启恢复、Redis 故障、过期、reset、delete 和跨用户会话隔离。

**验收条件：**任一预约事实可追溯到数据库；checkpoint 丢失不会导致错误写入；并发消息不会丢失或错序；摘要不能改变权限或业务状态；删除和保留行为符合产品说明。
